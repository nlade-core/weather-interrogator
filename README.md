# weather-interrogator

Short-term weather forecast for Edinburgh, pulled live from [Open-Meteo](https://open-meteo.com/) (no API key needed — safe for a static site). A chart navigates the raw hourly data into something readable; the raw JSON is still there, collapsed, for anyone who wants to check the tool's working.

Live: https://nlade-core.github.io/weather-interrogator/

## Why

Weather APIs return a wall of hourly arrays. Most questions people actually have ("do I need an umbrella," "is it worth a BBQ this weekend") only need a couple of those numbers, weighed together. This is a testbed for going from raw data to a useful answer.

## MVP (current)

- Fetch is pinned to `models=ukmo_uk_deterministic_2km` explicitly rather than `best_match` — same grid cell, same values for every field that's genuinely UKV (confirmed identical to best_match's), but a field UKV can't produce (like `precipitation_probability`, which needs an ensemble UKV doesn't have) comes back null instead of best_match silently substituting a mismatched ~27km source and us displaying it as if it were local. `precipitation_probability` is deliberately not fetched at all
- Chart shows temperature at 15-minute resolution (a visibly smoother, more precise line than hourly) with predicted rainfall as a full-height wash behind it, Apple Weather-style — bar **height is predicted amount in mm directly** (ceiling ~3mm/15min, solidly "heavy"), not probability. Both series share one time axis so they line up correctly; raw JSON available collapsed
- Precip wash is coloured by type (blue rain/drizzle, pale cyan snow, violet thunderstorm/hail) from `weathercode` — confirmed against the docs that weathercode is an *instant* reading, so it's a plain "most recent known reading" lookup
- Chart has a fixed-height condition-icon strip at the top (one icon per 15-min slot — genuine 15-min data, `weathercode` moved from the `hourly` fetch to `minutely_15` once confirmed it's derived per-timestep from `cloud_cover` etc. rather than hourly-native, so icons no longer repeat a stale value 4x), hour labels along the bottom (every hour, not every-other), and dual Y-axes: temperature on the left with "nice" round-number ticks, rainfall on the right (fixed 0/1/2/3mm — that's what bar *height* now encodes; type lives in colour, not position). The old inline "16°" point labels were removed — redundant now that there's both an axis for general scale and a working hover tooltip for exact values
- Condition icons ride the temperature line (Yr-style), tracking its curve rather than sitting in a fixed row — tried both, this reads better now that wind is a single compact glyph rather than two stacked rows, so there's no collision to avoid. Wind stays in its own fixed strip at the very top: a single arrow per 15-min point encoding both speed and direction in one glyph — rotation for direction, size (8-17px) for speed — rather than the earlier separate arrow+number pair where it was unclear which glyph the number belonged to; standard wind-vector convention (bigger = stronger), same idea as Windy/GFS wind maps. Exact value stays one hover away, same pattern as everything else on the chart
- Custom hover (dashed guide line, snapped highlight, floating tooltip) instead of native title-tooltips — same interaction pattern as Plotly/Yr, hand-rolled with no charting library
- "Ask" is wired to Chrome's built-in Gemini Nano (Prompt API) — on-device, no server. Edinburgh's 15-min temperature, 15-min rain amount (mm), 15-min wind (speed+direction), hourly wind gusts, and hourly conditions (type) for the rest of today are all baked into one persistent session's system prompt at creation time, so follow-up questions share context instead of starting fresh each time. Gusts get the same preceding-hour-max shift precipitation probability needed. No rain-probability figure is included — deliberately, since the only one available wasn't locally reliable
- Each question runs as two turns in that session rather than one: first a short "what does this need, is it covered" unpacking step, then the answer — small on-device models do better at combining two data series into a judgment when made to state what's needed before answering, rather than jumping straight there
- The model is pre-warmed at page load when it's already downloaded; a "downloadable" state waits for your first Ask click to trigger anything, with real download-progress percentages shown rather than a page that just looks stuck
- Chat-style log under Ask: your question right-aligned, the model's reasoning step and answer left-aligned and visually distinct, status/error lines centered — every state transition (preparing, downloading, understanding, answering, error) visible instead of failing silently
- No build step, no dependencies — plain HTML/CSS/JS

## Data notes

- Open-Meteo has no map/radar/tile imagery — point-location JSON only. For Edinburgh, the default `best_match` model resolves to the **UK Met Office's own UKV model (2km resolution)**, the best available option for this location, not a generic global grid.
- Historical **observed** data goes back to 1940 (reanalysis-based) via the Historical Weather API.
- Historical **forecast** data (what the model predicted, not what happened) is also available, separately: the **Previous Model Runs API** (`previous-runs-api.open-meteo.com`) returns past forecasts at fixed lead times (1-7 days ahead) via `_previous_dayN` suffixed variables — this is what a real probability-calibration check for Edinburgh would be built on, comparing predicted vs. observed rather than trusting either general model reputation or reasoned guesses. Caveat found while trying this: `precipitation_probability_previous_dayN` is always null — probability specifically isn't archived by this API, only deterministic fields (temp, amount, etc.) are
- **Confirmed UKV (2km) variable list**, checked by requesting `models=ukmo_uk_deterministic_2km` explicitly and seeing what's actually non-null (not assumed): `temperature_2m`, `apparent_temperature`, `dew_point_2m`, `relative_humidity_2m`, `vapour_pressure_deficit`, `precipitation`, `rain`, `snowfall`, `weather_code`, `cloud_cover` (+low/mid/high), `visibility`, `uv_index`, `pressure_msl`, `surface_pressure`, `wind_speed_10m`, `wind_speed_80m`, `wind_direction_10m`, `wind_gusts_10m`, `is_day`, `cape`, `freezing_level_height`, `soil_temperature_0cm`, `et0_fao_evapotranspiration` — all genuinely at 15-min resolution (checked consecutive values actually vary, not just the hourly figure repeated 4x). **Not** from UKV, comes from elsewhere under `best_match`: `precipitation_probability`, `showers`, `snow_depth`, `evapotranspiration`, `uv_index_clear_sky`, `soil_moisture_0_to_1cm`.
- The `_2m`/`_10m`/`_80m` suffixes are height-above-ground (temperature measured at 2m, wind at 10m and separately at 80m — standard WMO diagnostic heights), unrelated to the model's 2km horizontal grid spacing — easy to conflate, they're different axes entirely.
- Open-Meteo doesn't interpolate between grid points for a requested coordinate — it **selects one grid cell**, by default the on-land cell whose elevation (90m DEM) best matches the request, then statistically adjusts for any remaining elevation gap. Confirmed empirically: querying a fine mesh of ~170 points across ~10km around Edinburgh resolved to 28 distinct real grid cells with genuinely varying elevation (17-159m) and temperature (15.7-17.3°C) between neighbours — interpolating across those would wash out real terrain-driven local variation, not just smooth noise.
- `wind_speed_10m` is "instant" but behaves nothing like a real spot observation — checked empirically (same Gogarbank week, modeled vs. NOAA-observed hour-to-hour changes): the model's mean/stdev hour-to-hour jump was 1.16/1.13 km/h vs. the real station's 2.34/2.08 km/h — roughly **half the variance**. Read: a 2km/hourly-timestep model can't resolve real turbulence, so its "instant" wind is really the smoothed resolved-scale field with turbulence parameterized away, not a genuine point sample the way a real anemometer reading is — which is exactly why gusts exist as a separate variable. **Open question, deliberately not resolved:** does the same variance-reduction logic apply to *gusts*? Gusts are already an explicit extreme/max (not an average), so the "forecast converges toward the expectation" reasoning that explains temperature/sustained-wind's lower variance may not transfer cleanly. Flagged for later, not answered.
- Gogarbank's *archived* (NOAA ISD) cadence is confirmed hourly, on the hour — but that's what the archive retains, not necessarily the station's true native sampling rate.
- The Met Office has its own direct API (**Weather DataHub**) — confirmed to exist, confirmed it requires registration + an API key (unlike everything else this project uses), and confirmed it offers something Open-Meteo doesn't: actual map imagery (PNG, temperature/precip/cloud/pressure) plus a "Land Observations API" for ground-station data. **Not confirmed:** that observations API's exact cadence or whether there's a free tier — tried one docs page, it didn't have the answer, and deliberately stopped rather than keep guessing URLs. The forecast/model data itself is confirmed identical to what we already get via Open-Meteo (same UKV), so the only real reason to go direct would be map imagery or fresher observations, not better forecasts.

## Stack

Static HTML/CSS/JS, deployed via GitHub Pages. No build step, no API key, no tracking.

`css/style.css` and `js/app.js` are linked with a `?v=N` query string in `index.html`. Bump `N` whenever either file changes — Safari caches GH Pages assets aggressively and won't otherwise pick up the update.

The footer's "Deployed" timestamp is hand-set in `index.html` on every push (no CI/build step for a repo this size) — update it to the current Europe/London time alongside whatever else changed in that commit.
