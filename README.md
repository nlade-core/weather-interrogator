# weather-interrogator

Short-term weather forecast for Edinburgh, pulled live from [Open-Meteo](https://open-meteo.com/) (no API key needed — safe for a static site). A chart navigates the raw hourly data into something readable; the raw JSON is still there, collapsed, for anyone who wants to check the tool's working.

Live: https://nlade-core.github.io/weather-interrogator/

## Why

Weather APIs return a wall of hourly arrays. Most questions people actually have ("do I need an umbrella," "is it worth a BBQ this weekend") only need a couple of those numbers, weighed together. This is a testbed for going from raw data to a useful answer.

## MVP (current)

- Fetch is pinned to `models=ukmo_uk_deterministic_2km` explicitly rather than `best_match` — same grid cell, same values for every field that's genuinely UKV (confirmed identical to best_match's), but a field UKV can't produce (like `precipitation_probability`, which needs an ensemble UKV doesn't have) comes back null instead of best_match silently substituting a mismatched ~27km source and us displaying it as if it were local. `precipitation_probability` is deliberately not fetched at all
- Chart shows temperature at 15-minute resolution (a visibly smoother, more precise line than hourly) with predicted rainfall as a full-height wash behind it, Apple Weather-style — bar **height is predicted amount in mm directly** (ceiling ~3mm/15min, solidly "heavy"), not probability. Both series share one time axis so they line up correctly; raw JSON available collapsed
- Precip wash is coloured by type (blue rain/drizzle, pale cyan snow, violet thunderstorm/hail) from `weathercode` — confirmed against the docs that weathercode is an *instant* reading, so it's a plain "most recent known reading" lookup
- Layout, top to bottom: date (once) and hour labels at the top — the conventional position, not buried at the bottom — then the main plot with condition icons riding the temperature line's curve (Yr-style; genuine 15-min `weathercode` data, moved from `hourly` to `minutely_15` once confirmed it's derived per-timestep from `cloud_cover` etc. rather than hourly-native), one icon per 15-min point. Dual Y-axes: temperature on the left with "nice" round-number ticks, rainfall on the right (fixed 0/1/2/3mm — that's what bar *height* encodes; type lives in colour, not position). The old inline "16°" point labels were removed — redundant now that there's both an axis for general scale and a working hover tooltip for exact values. A change-triggered icon-thinning approach (only refresh at most every 30min) was tried and reverted — back to full 15-min density
- Wind: arrow (direction) + speed number at the bottom, one pair per 15-min point — tried merging into a single size-scaled arrow (bigger = stronger, no separate number) but reverted; the explicit number reads more clearly than inferring speed from size alone. Exact value also available via hover, same pattern as everything else on the chart
- Custom hover (dashed guide line, snapped highlight, floating tooltip) instead of native title-tooltips — same interaction pattern as Plotly/Yr, hand-rolled with no charting library
- "Ask" is wired to Chrome's built-in Gemini Nano (Prompt API) — on-device, no server. Edinburgh's 15-min temperature, 15-min rain amount (mm), 15-min wind (speed+direction), hourly wind gusts, and hourly conditions (type) for the rest of today are all baked into one persistent session's system prompt at creation time, so follow-up questions share context instead of starting fresh each time. Gusts get the same preceding-hour-max shift precipitation probability needed. No rain-probability figure is included — deliberately, since the only one available wasn't locally reliable
- Each question runs as two turns in that session rather than one: first a short "what does this need, is it covered" unpacking step, then the answer — small on-device models do better at combining two data series into a judgment when made to state what's needed before answering, rather than jumping straight there
- The model is pre-warmed at page load when it's already downloaded; a "downloadable" state waits for your first Ask click to trigger anything, with real download-progress percentages shown rather than a page that just looks stuck
- Chat-style log under Ask: your question right-aligned, the model's reasoning step and answer left-aligned and visually distinct, status/error lines centered — every state transition (preparing, downloading, understanding, answering, error) visible instead of failing silently
- No build step, no dependencies — plain HTML/CSS/JS

## Roadmap

- [x] **Built (2026-09-08): Ask pipeline rebuilt around `responseConstraint` (schema-constrained model output), ported from a standalone test bench after six rounds of testing against the real on-device model.** The bench (`data/ask-parsing-test.html`, gitignored — not shipped, kept locally as the record of how each fix was found) ran the full pipeline against 8 representative questions, fixing one confirmed failure at a time rather than redesigning speculatively. What shipped:
  - **The old free-text-plus-regex category matcher (`CATEGORY_MATCHERS`/`matchCategories`/`DEFAULT_CATEGORIES`) is gone**, replaced by `buildParseSchema()` + Chrome's Prompt API `responseConstraint` — the model's output is now structurally forced to match a JSON Schema rather than hoping a regex catches whatever free text it produced.
  - **`applicable` field, the only required one.** First bench run showed "what about this weekend?" and "what's your favourite colour?" both getting a confident-looking, fabricated data extraction — the old schema had no way to say "I can't answer this." A question flagged `applicable: false` now gets a fixed decline message with no further model call, rather than a forced pick.
  - **`timeScope` (3 buckets: `next_few_hours`/`today`/`whole_window`), not always the full window.** Previously every question got data across the entire `CONTEXT_HOURS` regardless of what was actually asked — "will it be nice in an hour" and "how do the next couple of days look" got identically-sized lookups. Started at 4 buckets, collapsed to 3 after bench testing showed the same question picking a different bucket on repeat runs (sampling params aren't available to a plain web page, only Chrome Extensions — checked before assuming a fix was possible there — so fewer buckets to disagree with itself across was the actual fix).
  - **Day-grouped, summarized extraction — the biggest correctness find.** `formatHour` only ever returned bare HH:MM; at wide time scopes the series spans 2-3 calendar days, so hours genuinely repeated with no way to tell which occurrence was which. This produced a real wrong answer in testing ("bring an umbrella" despite 0.0mm forecast every hour) and a garbled, duplicated-timestamp answer even after the wrong-conclusion part got fixed. `lookupWeatherData` now groups every category by day (`[Today] ... [Tomorrow] ...`); `conditions` additionally collapses consecutive identical readings into ranges instead of one entry per hour; `rain` collapses to one line when every extracted value is dry instead of dozens of "0.0mm" repeats.
  - **A deterministic rain-inclusion rule**, not a fifth prompt-engineering attempt. Four straight rounds (schema description, then two worked examples) failed to get the model to reliably pick `rain` for implicit/activity-suitability questions ("is it worth a BBQ" never once self-selected it, six bench runs straight) — rain is now added automatically whenever `wind` or `temperature` is picked without it, since the data is cheap to include and rarely wrong to have.
  - **An explicit "plain prose, not JSON" instruction on the final answer call.** Bench testing found the same session, right after a `responseConstraint` turn, sometimes just re-emitting that turn's JSON instead of switching back to free text on the next call — a real reliability gap found in a bench rather than shipped straight to users.
  - Verified with synthetic data (not just visually) before shipping: the day-grouping and all-dry-rain-shortcut logic were dry-run tested in Node against arrays crossing real multi-day boundaries, confirming correct day-splitting and shortcut behaviour, before being pasted into the real fetch-shaped code.
  - Not yet re-verified in real Chrome after this specific port — the bench validated the *design*, but this is a fresh copy into different surrounding code (raw index arrays vs. the bench's normalized row table), worth a real run-through before considering this settled.

- [x] **Built (2026-09-08): "Coming days" panel removed, chart/Ask window widened to UKV's full real range (54h / 2¼ days).** Direct follow-through from the accuracy investigation two days prior — decided against blending sources anywhere in the app (the multi-model comparisons stayed a separate side investigation, never wired in), so the natural next step was making the *shipped* app match that: one display, UKV only, its actual range.
  - `CONTEXT_HOURS` (shared by the chart's forward span and the Ask/LLM context window) went 12 → 48 → 54 across two passes. First pass landed on 48 after checking the *live* forecast endpoint specifically (a different mechanism from the archival Single Runs API the accuracy work mostly used) and finding real coverage from "now" drifts between ~50-54h depending on where "now" falls relative to the latest 3-hourly run — 48 was a safety margin under that. Asked to push to the literal 2¼-day ceiling instead, which meant handling the null-tail risk properly rather than avoiding it: `tempIdxs` (chart) and the Ask lookup's hourly index lists now filter out null readings explicitly, rather than assuming the whole nominal window is always populated. A short blank gap at the chart's right edge on some loads is the honest result, not a bug to hide.
  - Icon/label density needed real handling, not just a bigger number: at ~51h span, one glyph per 15-min point is ~200 marks, checked and genuinely illegible. Condition icons and wind arrows now render hourly; axis labels tick every 3h. The underlying `points` array (hover, precip wash, axis scaling) stays full 15-min throughout — only the always-visible glyph layer got coarser, same principle the old inline temperature labels were dropped for (hover already carries exact values).
  - Ask's per-category data also moved from 15-min to hourly cadence, for a different reason than the chart's: 48h+ at 15-min is ~190 entries per category, a real context-budget concern for an on-device model that the old 12h version never had to consider. Rain's hourly figure sums that hour's four 15-min readings rather than reusing the chart's single-quarter shift, which would have silently described only the last 15 minutes of each hour.
  - **Real bug caught before shipping, not after**: the "what's driving today" dominant-factor callout took the entire forward window unscoped. Widening `CONTEXT_HOURS` without touching it would have silently let "main factor today" describe something at 3am the day after tomorrow. Bounded to today's calendar date specifically at the call site.
  - `buildExtendedDailyUrl`, `renderDailySummary`, and `dailyCardHtml` removed entirely, along with the `daily` fetch param (no longer used by anything) and the now-dead `.daily-*` CSS. The non-UK quality caveat that used to live in the removed panel's note text was moved into the subtitle instead, rather than dropped — it was the only place on the page telling a non-UK user their data is a coarser model, and that's still true.
  - Not yet verified in a real browser by this session — no headless/screenshot tool available here. Opened locally and the logic was traced carefully, but the actual render (icon spacing, precip-wash density at ~200 packed 15-min bars, axis readability across a 2-3 day span) needs a real look before calling this settled.

- [x] **Built (2026-09-07): temperature and wind split into two stacked graphs, each with its own sensibly-calibrated scale**, replacing the single fixed 0-25 shared scale (C and mph forced to mean the same height, always a deliberately-simple placeholder). Temperature rounds to the nearest 5 above/below the actual data range; wind is floored at 0 (can't be negative) with a ceiling rounded up to the nearest 5 above the max. Rain stays a wash behind the temperature graph rather than becoming a third stacked graph or moving to the wind one — decided, not defaulted: temp+rain is the pairing that actually answers "what to wear, is it worth going out" (the Apple-Weather-style pairing this chart started from), wind is more often the secondary factor per the dominant-factor heuristic elsewhere on this page. Worth revisiting as its own graph later if it reads as cluttered now that wind isn't sharing vertical space with it any more.
  - Both graphs share one time axis (date/hour labels sit once, at the top, serving both) and one continuous "now" marker line spanning across both panels and the gap between them, rather than two separate markers — the usual convention for a shared-x-axis multi-panel chart.
  - Hover/touch now drives two dots (one per graph) from a single shared crosshair and hit-area spanning both panels, so one interaction updates both at once rather than needing to hover each graph separately.
  - Night-band shading now draws on both graphs (previously one shared region) since both share the same time axis and "is it dark right now" applies to both.
  - **Real bug caught by screenshot, not assumed correct from the code**: wind axis labels ("20mph" etc.) were genuinely clipped against the SVG's own left edge — the temp axis's short "20°" labels fit fine at the same `padLeft`, but "mph"-suffixed labels are enough wider that the leading digit got cut off. Only visible in an actual render, not from reading the tick-generation code. Fixed by widening `padLeft` slightly and dropping the repeated "mph" suffix per tick in favour of bare numbers plus one small unit label above the axis — same fix shape as the "estimate" badge collision from the daily-summary work the day before.
  - Verified with real data (screenshots at desktop and 390px mobile widths, both after the fix) and confirmed the two hover dots land at genuinely different y-coordinates during a real hover interaction, not just visually plausible.

- [ ] **Unpacked (2026-09-06), not built: measuring and displaying forecast accuracy.** Two fundamentally different comparisons, answering different questions: (A) against real observations — NOAA ISD (Gogarbank, already integrated once for the wind-variance investigation) or the Met Office Land Observations API (needs a key, already a dead end) — true ground truth, but the station sits 2.1km from the city centre and only reports hourly; (B) against the model's own later revisions — the Previous Model Runs API (already found while chasing the precipitation-probability question earlier this session) archives what was predicted at fixed lead times, free, no separate fetch architecture, but only measures self-consistency, not correctness — a confidently, consistently wrong model would score perfectly. Real accuracy needs (A); (B) is a cheap always-available proxy, and the one that actually fits this app's constraints, since it needs zero persistence (query fresh on every page load, unlike (A) which would need to accumulate observations over time).
  - **Metrics should be per-variable, not one blended score** — this project's own findings already show why: temperature wants plain mean-absolute-error, rain needs a hit/miss/false-alarm framing (did it rain when predicted, not just the mm delta) since a probability figure was deliberately dropped, and wind's already-documented lower-variance-than-reality issue (checked against Gogarbank early this session: modeled hour-to-hour variance was roughly half the real station's) means a naive MAE would flatter the model for a structural limitation, not genuine skill.
  - **Why it'd matter, specifically, not generically:** trustworthiness already varies by variable in this project's own findings (wind's smoothed turbulence, `precipitation_probability`'s resolution mismatch, `apparent_temperature` folding in humidity) — a visible accuracy record lets someone calibrate trust per-variable rather than treating every number at equal weight, the retrospective sibling of the dominant-factor heuristic already shipped. Also the quantitative counterpart to the webcam feature's whole premise (compare forecast to reality) — right now that comparison is anecdotal, this would make it a running number.
  - **Recommended starting point, if this gets built:** the Previous Model Runs route, not real observations — a small "yesterday's forecast for right now said X, it's actually Y" callout, computed fresh each load, reusing the same recent-past visual language already built for the chart's trailing strip. Cheaper than integrating NOAA ISD properly, no new persistence pattern, and answers the more common user question ("has this been flaky lately") even without answering the deeper one ("was it actually right"). Needs a real design pass before building, same as the relative-importance item above — not scoped further than this yet.
  - **Correction (2026-09-07): the "2.1km from the city centre" Gogarbank figure above is wrong.** Recomputed via haversine on the real station coordinates (isd-history.csv, station `031660-99999`): Gogarbank is **~10.3km from central Edinburgh**, not 2.1km — that 2.1km figure is Gogarbank's distance from Edinburgh *Airport*, a stale mixup from an earlier session. Also confirmed the NOAA ISD bulk archive (`ncei.noaa.gov/data/global-hourly`) has a **~13-month publication lag** (checked directly: 2025-08-24 was the newest available record when queried in September 2026; Heathrow's file showed the identical cutoff, so it's NCEI's general QC/archival lag, not a Gogarbank-specific outage). Between the distance and the lag, Gogarbank is not a usable *live* ground-truth source for this app — only a candidate for a one-off offline calibration exercise using year-old data.
  - **Extensive follow-up investigation (2026-09-07), still not built into the app — real numbers now exist, not just a plan:**
    - **UKV's real forecast ceiling, confirmed empirically at hourly resolution:** using Open-Meteo's Single Runs API (`single-runs-api.open-meteo.com`, `run=` parameter selects one specific past model initialisation), a single UKV run returns continuous 15-min data from lead=0 out to **~54h45m and then hard-stops** (requested 10 days from one run, got real data through hour 219/54.75h, null after) — this is UKV's actual operational forecast length, not an API or archival limit. Matches the earlier, independently-found "`daily` block only populated for 2 days" result from the app's own MVP work — two different mechanisms landing on the same ~2.25-day ceiling.
    - **Built real empirical error distributions (boxplots, |predicted − actual| and signed, by lead hour) from three independent UKV samples, and watched the answer change as the sample grew:**
      - 168 runs (3 weeks, mid-Aug–early-Sept 2026, one season slice) → 24h median error 0.50°C, signed bias **+0.10°C** (looked slightly warm).
      - 1,248 runs (~5 months, April–September 2026, full Single Runs archive at the time) → 24h median error 0.50°C, signed bias **−0.10°C**.
      - `previous_day1` field, 17,274 hourly samples (full ~2-year archive, Aug 2024–Sept 2026) → 24h median error 0.60°C, signed bias **−0.20°C**.
      - **The bias flips sign between the small and large samples, and the two large, methodologically-independent samples agree with each other on the flipped sign.** Real lesson, not a footnote: 168 samples from one 3-week window was enough to get the *typical* error about right (0.50°C either way) but wrong the *sign* of a systematic bias — worth remembering before trusting any single-window sample in this project again.
    - **Cross-checked against a second model entirely, to see if UKV's advantage is real:** GFS (`gfs_seamless`) vs ERA5-Land, one full year, 8,664 hourly samples per lead-day. Grid-cell selection matters a lot at this coarser resolution — checked several long-range models for which grid node actually lands closest to central Edinburgh: ECMWF IFS resolves 22.9km away, ICON resolves 0.9km away but its archive has no `previous_day7` field, GFS resolves 2.2km away with all seven day-offsets populated — used GFS as the best available combination. Result: GFS's day-1 median error (0.70°C) is worse than UKV's (0.50–0.60°C depending on sample), and GFS carries a real, consistent **+0.3°C warm bias at every lead day from 1 to 7** — three times the size of UKV's own bias. Unlike UKV's hourly error (which saturates within about half a day and stays flat out to 54h), GFS's daily error grows roughly linearly across the whole week, no plateau reached within 7 days.
    - **UKV genuinely cannot produce a 7-day forecast, at any resolution** — confirmed via two independent mechanisms above (hourly ceiling ~54h45m; daily block empty past day 2), so the "Coming days" panel's own days 3-7 were already correctly sourced from a *different* fetch (`buildExtendedDailyUrl`, no `models` param → Open-Meteo's `best_match` blend) and visually marked as an estimate — there is no missing UKV data to go find for days 3-7, because UKV was never the source for them in the first place.
    - **Confirmed (2026-09-07, not yet pulled): the app's actual days-3-7 source is directly checkable the same way GFS was, no proxy needed.** `best_match` (the exact unpinned fetch `buildExtendedDailyUrl` uses) supports the full `previous_day1`...`previous_day7` mechanism — checked directly, all four spot-checked offsets (1/3/5/7) came back populated. Next step, if pursued: repeat the GFS-style backfill on `best_match` itself rather than a GFS stand-in, pull the longest available history from the start this time (the UKV bias-sign lesson above says not to trust a short window), and settle what "actual" to score it against — ERA5-Land as before, or archive-api's own unpinned default (not yet checked what that resolves to).
    - **All raw pulled datasets kept local and gitignored, not committed** — `weather-interrogator/data/` (excluded via `.gitignore`), largest file `ukv-singleruns-full-2026-04to09.json` at 4.2MB / 67,247 rows. Deliberately kept out of the repo history and out of the shipped app; this was investigation, not a feature.

  **Feasibility, verified, not assumed:** Open-Meteo's `past_days` fetch parameter extends both `minutely_15` and `hourly` arrays backward by full calendar days, at the *same* resolution as the forward data (confirmed via `past_days=1`: `minutely_15` came back 192 points spanning two full days instead of one, still genuinely 15-min throughout, `hourly` likewise). No separate past-data endpoint or resolution downgrade — same one-fetch architecture as everywhere else in the app. Note `past_days` grants whole extra calendar days from midnight, not "N hours before now" — getting e.g. "past 3 hours" means fetching `past_days=1` and then slicing with the same `nextHoursIndices`-style windowing already used for the forward side, just walking backward from `now` instead of forward.

  - **`PAST_HOURS = 3`**, kept deliberately shorter than the 12h forward window so it reads as context, not a second panel.   - **Now marker**: a new always-visible vertical line + "now" label (`chart-now-marker`/`chart-now-label`), distinct from the existing hover guide which only appears on interaction. **Past de-emphasis**: `chart-past` class at 45% opacity on condition/wind icons directly, but precip bars needed a different approach — `.precip-bar` already sets its own opacity per type (rain/snow/storm), so adding a second opacity class to the *same* `<rect>` would just override it via the CSS cascade (the exact presentation-attribute-vs-class precedence bug this project hit once before with the wind icons), losing the type distinction. Fixed by wrapping past bars in their own `<g class="chart-past">` instead — group opacity compounds with a child's own opacity rather than colliding with it.
  - **`xForTime`/`spanMs` reworked** to offset from `windowStart` (`now - PAST_HOURS`) rather than `now` — touched, as expected, since every other position on the chart derives from it.
  - **Night-band and axis code needed zero changes**, confirming the earlier prediction — neither assumed `now` was the left edge.
  - **Real bug caught during testing, not before shipping:** `past_days=1` (added for this) also shifts the *daily* summary's array — `daily.time[0]` becomes yesterday instead of today whenever `past_days` is set, which broke the hardcoded index-0-is-today assumption in `renderDailySummary` (below) and was only caught because testing showed three day-cards instead of two. ## Data notes

- **What's UKV and what isn't, for a UK location (updated 2026-09-08 — the "Coming days" panel described below as of 2026-09-07 has since been removed, see Roadmap) — the priority reference for any future frontend work on this:**
  - `buildForecastUrl` (the main fetch, `js/app.js:13`) is pinned to `models=ukmo_uk_deterministic_2km` whenever `LOCATION.isUK`. This single fetch supplies **the entire page**: `current`, `minutely_15` (temp, feels-like, precipitation, wind speed+direction, weathercode, is_day — the chart's whole 15-min line), and `hourly` (wind gusts only). No `daily` block any more — see below. All of it is genuine 2km UKV.
  - **As of 2026-09-08, there is no non-UKV data anywhere in the app for a UK location.** The "Coming days" panel (`buildExtendedDailyUrl`, `best_match`, days 3-7) was removed rather than kept — this app now shows only UKV's own real range, full stop, one display. `CONTEXT_HOURS` (chart span and Ask/LLM window both) is set to 54, UKV's actual ceiling, not a smaller safety-margin number — see the CONTEXT_HOURS comment in `js/app.js` for how the resulting occasional-null-tail risk is handled (filtered, not avoided).
  - For a **non-UK** location, none of this pinning applies — `buildForecastUrl` itself omits `models` too (UKV has no non-UK coverage), so *everything* comes from `best_match`. The app says so in the subtitle (`setLocationCopy` in `js/app.js`) rather than implying UK-grade quality it doesn't have there.
- Open-Meteo has no map/radar/tile imagery — point-location JSON only. For Edinburgh, the default `best_match` model resolves to the **UK Met Office's own UKV model (2km resolution)**, the best available option for this location, not a generic global grid.
- Historical **observed** data goes back to 1940 (reanalysis-based) via the Historical Weather API.
- Historical **forecast** data (what the model predicted, not what happened) is also available, separately: the **Previous Model Runs API** (`previous-runs-api.open-meteo.com`) returns past forecasts at fixed lead times (1-7 days ahead) via `_previous_dayN` suffixed variables — this is what a real probability-calibration check for Edinburgh would be built on, comparing predicted vs. observed rather than trusting either general model reputation or reasoned guesses. Caveat found while trying this: `precipitation_probability_previous_dayN` is always null — probability specifically isn't archived by this API, only deterministic fields (temp, amount, etc.) are
- **Confirmed UKV (2km) variable list**, checked by requesting `models=ukmo_uk_deterministic_2km` explicitly and seeing what's actually non-null (not assumed): `temperature_2m`, `apparent_temperature`, `dew_point_2m`, `relative_humidity_2m`, `vapour_pressure_deficit`, `precipitation`, `rain`, `snowfall`, `weather_code`, `cloud_cover` (+low/mid/high), `visibility`, `uv_index`, `pressure_msl`, `surface_pressure`, `wind_speed_10m`, `wind_speed_80m`, `wind_direction_10m`, `wind_gusts_10m`, `is_day`, `cape`, `freezing_level_height`, `soil_temperature_0cm`, `et0_fao_evapotranspiration` — all genuinely at 15-min resolution (checked consecutive values actually vary, not just the hourly figure repeated 4x). **Not** from UKV, comes from elsewhere under `best_match`: `precipitation_probability`, `showers`, `snow_depth`, `evapotranspiration`, `uv_index_clear_sky`, `soil_moisture_0_to_1cm`.
- The `_2m`/`_10m`/`_80m` suffixes are height-above-ground (temperature measured at 2m, wind at 10m and separately at 80m — standard WMO diagnostic heights), unrelated to the model's 2km horizontal grid spacing — easy to conflate, they're different axes entirely.
- Open-Meteo doesn't interpolate between grid points for a requested coordinate — it **selects one grid cell**, by default the on-land cell whose elevation (90m DEM) best matches the request, then statistically adjusts for any remaining elevation gap. Confirmed empirically: querying a fine mesh of ~170 points across ~10km around Edinburgh resolved to 28 distinct real grid cells with genuinely varying elevation (17-159m) and temperature (15.7-17.3°C) between neighbours — interpolating across those would wash out real terrain-driven local variation, not just smooth noise.
- `wind_speed_10m` is "instant" but behaves nothing like a real spot observation — checked empirically (same Gogarbank week, modeled vs. NOAA-observed hour-to-hour changes): the model's mean/stdev hour-to-hour jump was 1.16/1.13 km/h vs. the real station's 2.34/2.08 km/h — roughly **half the variance**. Read: a 2km/hourly-timestep model can't resolve real turbulence, so its "instant" wind is really the smoothed resolved-scale field with turbulence parameterized away, not a genuine point sample the way a real anemometer reading is — which is exactly why gusts exist as a separate variable. **Open question, deliberately not resolved:** does the same variance-reduction logic apply to *gusts*? Gusts are already an explicit extreme/max (not an average), so the "forecast converges toward the expectation" reasoning that explains temperature/sustained-wind's lower variance may not transfer cleanly. Flagged for later, not answered.
- Gogarbank's *archived* (NOAA ISD) cadence is confirmed hourly, on the hour — but that's what the archive retains, not necessarily the station's true native sampling rate.
- The Met Office has its own direct API (**Weather DataHub**) — confirmed to exist, confirmed it requires registration + an API key (unlike everything else this project uses), and confirmed it offers something Open-Meteo doesn't: actual map imagery (PNG, temperature/precip/cloud/pressure) plus a "Land Observations API" for ground-station data. **Not confirmed:** that observations API's exact cadence or whether there's a free tier — tried one docs page, it didn't have the answer, and deliberately stopped rather than keep guessing URLs. The forecast/model data itself is confirmed identical to what we already get via Open-Meteo (same UKV), so the only real reason to go direct would be map imagery or fresher observations, not better forecasts.
